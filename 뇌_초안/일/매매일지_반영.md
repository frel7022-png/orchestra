# 매매일지 반영

## 설명
- **무엇을 내놓나(끝까지)**: 매매일지를 받으면 숫자를 **만드는** 일이다 — 매매일지는 그날 하루 전체의 누적이라 같은 날짜를 통째로 바꿔 넣고 〔일과에서 옮김〕, 반영 → 출력 확인 → DB 점검 → 데이터 파일만 커밋까지 묻지 않고 간다. 끝에 대표에게 날짜별 매수·매도 건수, 보유 수, 예수금, 커밋 id와 "메리츠 화면이랑 맞는지 봐 줘" 한 줄. **섹터 지정은 매번 대표에게 한 줄로 묻는다**(원-2026-10-23-11). **두 계좌 맞추기(sync)는 반영한 날마다 묻지 않고 장 마감 뒤**(원-2026-10-26-03 — 대체됨: 매번 묻기 원-2026-10-23-11). 설계도실은 출력이 이상할 때만 내려간다.
- **언제 시키나**: **들어오면 반영한다 — 대표가 그날 매매일지를 언제 넣든**(원-2026-10-29-15: 시각이 아니라 사건으로 도는 일). 대표 "넣었어"·"반영해"·"올렸어"(todaytrans/에 메리츠 매매일지 CSV) · 예탁금 이용료(입금)가 들어왔을 때 〔일과에서 옮김〕 · 마감본이 와서 같은 날짜를 다시 넣을 때 · 지난 날짜를 다시 넣을 때. 부르는 말: 넣었어, 반영해, 올렸어, 매매일지, 마감본.
  - 파일은 `todaytrans/`에 대표가 넣는다 — 나는 폴더를 감시하지 않으니 말이 있어야 시작한다.
  - 가르는 법:
    - 숫자를 **만드는** 일이면 이 일, **말하는** 일("지금 어때?")이면 `지금_숫자.md`.
    - "이자 들어왔어"·배당 입금이면 CSV가 아니라 입금 행 한 줄 — 세션 장부 C5(데이터센터 게시판).
    - 오늘 첫 대화면 우편함 → 출근 점검이 먼저(지침서 2절).
- **얻을 것과 찾을 곳**(순서 아님 — 어디부터 볼지, 그 게시판에서 어느 사무실을 고를지는 그때 판단, 원-2026-10-27-12 · 위크 1027 「길에서 직접 정보를 빼고 게시판을 보고 판단」)
  - **이 일이 뭔지, 무엇을 하면 안 되나**(저장고·금지·자주 틀린 곳) → 아래 권한 · 자주 틀린 곳 · 입구 `python ingest_daily.py todaytrans/파일 YYYY-MM-DD`. ⚠시점 ⚠dtype — 숫자가 이상하면 holdings를 고치지 말고 transactions를 본다.
  - **외인 DB가 빠짐없이 쌓였나**(하루만 비어도 외인 기간 계산이 틀어진다) — `출근_점검.md`(점검 층만 빌림) · 입구 `python check_daily_db.py`.
  - **무엇을 어떻게 남기나**(데이터 파일만 이름으로 add · 반영한 날마다 장 마감 뒤 sync — 원-2026-10-26-03) → `../일과/기록_올리기.md`(이 일의 무엇)
  - 그 종목이 **사건**인가 — 보유 종목이 무상증자·분할을 했으면 아래 걸음 3b(수량 대조) → 관측소 게시판
  - 지금이 장중인가(`date +%H%M`) — 장중 파일인지가 보고 문장과 다시 넣을지를 가른다.
  - 코드 쪽(설계도실)은 아래 멈춤 "설계도실로 내려갈 때"만 — 평소엔 코드가 한다.
  - **무엇으로 재나** 〔일과에서 옮김 — 줄째〕
    - `ingest_daily.py 파일 날짜` — 반영·재계산 + 계좌 줄을 그날부터 마지막 날까지 다시(시장 줄은 빈 날만(원-2026-10-29-18·20)).
    - `daily_close.py [날짜]` — 15:35 예약(Orchestra_KRXClose 끝)이 부르는 하루 값 매기기: 빠진 날부터 그날까지 계좌 줄 + 그날 시장 줄. 파일만 찍고 커밋은 세션.
    - 정합성 검사 `check_history_alignment` = asset·sector·index·bigcap **4파일의 마지막 날짜만** 본다(`portfolio_core.check_history_alignment`) — 중간에 빈 날, 값이 장중값인지는 못 본다. fund_nav는 검사 밖.
    - `fix_sector.py 종목명 섹터` — 섹터 세 파일 + 체크포인트.
    - **증권사 실현손익 칸은 버린다**: 매매일지 CSV엔 수수료·세금까지 뺀 증권사 실현손익(`parse_daily_trade_csv`의 `실현손익_증권사`, 열 위치 `c[12]`)이 있지만, `import_daily_trades()`는 이 값을 버리고 `"실현손익": ""`로 저장한다 — 실현손익은 거래 재생(`apply_transaction`)이 만든다(transactions가 유일한 진실). 이유: 2026-08-18 앱 실현손익이 증권사 "당일실현"보다 몇백 원씩 크게 나왔을 때(그땐 실현손익에 수수료·세금 미반영, 예수금은 정확) 이 칸을 쓰면 맞출 수 있다는 것까지 확인했으나 대표 「몇백 원 차이니 넘어가자」로 보류. 2026-09-08 세금 모델 교체(매도 때 매도금액 × fee_rate를 실현손익에서도 뺌)로 그 오차는 해소됐다. 대표가 증권사 숫자와 정확히 맞추자고 하면 이 칸을 쓰는 게 출발점. [옮김] 옛 ARCHIVE §6-4 · 옛 claude.md §6-4
- **걸음** (2026-10-22 옛 주소 일과/매매일지_반영 절차·멈출 때에서 옮김 — 걸음 번호는 다른 장이 부르는 이름이라 그대로)
  1. 파일 이름(예: `todaytrans/1020.csv`)에서 날짜를 읽는다. 날짜는 ingest의 두 번째 인자다 — 스크립트는 파일 이름을 안 보니 세션이 읽어 넣는다(`ingest_daily.main`). 여러 날·같은 날 다시 옴은 아래 멈춤.
  2. `python ingest_daily.py todaytrans/파일 YYYY-MM-DD` — 그 날짜의 기존 반영분을 지우고 이 파일로 바꾼 뒤 재계산(체크포인트 경로). "최근 3일"은 **실행한 날부터 달력 3일**이다(`today − timedelta(days=3)`, `@뇌 safety_days_컷오프`) — 그보다 앞 날은 체크포인트로 굳는다(월요일에 돌리면 금요일이 이미 굳을 수 있다). 굳은 날을 다시 넣어도 ingest가 체크포인트를 버리고 전체 재생한다(`@뇌 체크포인트_막이`, 대표 결정 1 2026-10-21).
  3. 확인 칸대로 출력을 읽는다. 출력이 깨져 보이면 `check_history_alignment(날짜)`를 따로 부른다. ingest 끝 "실제 메리츠 앱 화면과 대조하세요"(`@뇌 메리츠_화면대조`)가 행 잘림을 잡는 유일한 그물이다 — 파서는 열 < 13·행 < 2만 막는다. 세션은 보유 수 급감만 보고, 최종 대조는 대표가 메리츠 앱 화면으로 한다.
  3b. **보유 종목에 무상증자·분할이 있었으면**(그날 공시 · 하루 등락이 가격제한폭 밖) 증권사 CSV 수량과 앱 보유 수량을 대조한다. 거래 반영 코드엔 분할·무상 거래 유형이 없고 매도 분기는 수량 부족을 확인하지 않는다 — 수량이 안 맞은 채 두면 나중에 늘어난 주식을 팔 때 옛 줄을 지우고 (매도가 − 옛 평단) × 판 수량으로 **가짜 큰 실현손실**이 잡힌다(새 뇌 코드 확인 10-26 밤 · 위크 2차 채점 T2, 옛 뇌가 짚음). 안 맞으면 고치지 말고 대표에게(입력은 대표 몫 — 코드 고치기는 이관 뒤, `../대기.md`). [새]
  4. 시세·코드 보충은 ingest가 매번 무조건 한다(`refresh_all_prices`, `@뇌 시세_무조건_갱신`) — 세션은 `[경고]` 줄만 읽는다. 새 종목은 **반영 날 바로** watchlist(csv + Supabase)에 들어가고(ingest 끝 백필), 시세·외인은 **그 종목 시작일부터** 채운다 — 섹터는 비슷한 기존 섹터(기타2 금지)(대표 10-22 17:4x 새 종목 등재 원칙, 「이건 튜즈데이도 마찬가지야」). 섹터가 기타2로 잡히면 아래 멈춤 "새 종목 섹터".
  5. 외인 DB 점검 → `출근_점검.md`(점검 층).
  6. 데이터 파일만 이름으로 묶어 commit·push → `../일과/기록_올리기.md`. **반영한 날마다 묻지 않고 sync** — 장 마감(15:30) 뒤, 장중본이면 16:00 뒤 같은 날짜 재반영 **다음에** `python sync_both_accounts.py` → new1·meritz 두 레포 `both_accounts.csv` 각각 commit·push(대표 「그렇다면 매일해」 원-2026-10-26-03). sync는 VIP 패널 상대 계좌 선용 파일 하나만 다시 쓴다 — 계좌 줄은 ingest가 그날부터 다시 덮었고, 시장 줄(혼합지수 · 지수)은 15:35 `daily_close`가 따로 찍는다(원-2026-10-29-18·20). meritz 칸은 meritz 매매일지가 멈춘 날 뒤로 빈칸 그대로(지어낸 값 없음 — 대표 「매리츠 매매일지는 나중에 빠진거 한번에 다 넣을 게. 그 때 수정하자」). 대체됨(10-26 15:1x): meritz 몰아 넣는 날에만(원-2026-10-26-02) · 대체됨(10-26 아침): 묻고 응이면(원-2026-10-23-11) · 대체됨(10-23): 묻지 않고 sync.
  7c. **케이스북**: 그날 **전량매도로 끝난 사이클**이 있으면 `python casebook.py` → `casebook/` 커밋(수급 게시판 절차 3 "케이스북 갱신" — 사무실은 "주간 리포트 때"라 늦어도 그 주 금요일엔). 사이클 종료 = 그날 판 종목 중 지금 보유 0. 자동으로 부르는 곳이 없다(마지막 커밋 10-20). 〔"옛 뇌가 손으로 하던 정기 일" 쓸기(87 → 새 뇌, 위크 지시 origin 대표 · Week 주민센터 손으로_하던_일_1026)〕 [새]

     - **장중에 넣은 날은 마감 뒤 같은 날짜로 한 번 더** — 확인 칸(원-2026-10-29-15 · 위크 결정 2026-10-20). 다시 넣는 까닭은 **그날 매매가 더 있었을 수 있어서**(마감본)다 — 값(계좌 · 시장 줄)은 15:35 `daily_close`가 KRX 종가로 찍고, 늦게 넣어도 ingest가 그날부터 KRX로 다시 덮는다(원-2026-10-29-18·20). 대체됨(2026-10-29): "그래야 asset·sector·index·bigcap 그날 행이 확정 종가로 바뀐다 · ingest는 그날 한 행만 쓴다 · 1600 이상인지 본다".

## 멈춤
- **멈추고 묻는다**: 파싱 실패 · 보유 수가 크게 이상 · 종목코드가 끝내 안 풀림 · git 충돌이나 내가 안 바꾼 파일(단 15:35 `daily_close`가 쓴 히스토리 다섯(asset · sector · index · bigcap · bench_history)이 M이면 내가 안 바꾼 파일이 아니다 — 출근 점검 1b에서 커밋한다(원-2026-10-29-18)). 그 밖엔 묻지 않고 끝까지 — 단 새 종목 섹터 지정은 매번 한 줄로 묻는다(원-2026-10-23-11).
- **파일이 `todaytrans/`에 없다**(대표가 "넣었어"라는데 그 날짜 파일이 없음) → 반영하지 않고 파일 이름·날짜를 묻는다. 옛 파일로 반영하지 않는다. 〔빈 세션 시험 13〕
- **장중 파일** → 보고에 "장중까지". 마감 뒤 한 번 더는 확인 칸(원-2026-10-29-15).
- **여러 날** → 오래된 날부터. 같은 날 여러 장이면 가장 늦은 것만.
- **이미 반영한 날이 다시 오면**(장중본 뒤 갱신본 · 여러 날 묶음에 지난 날이 섞임) → **새 것으로 통째로 교체**한다. 대표가 그날 일지를 준 뒤에도 매매해서 갱신본이 새로 온 것이다(대표 10-22 가-3, 원-2026-10-22-07). ingest가 그 날짜 반영분을 지우고 바꾼다(§1-2 "그날 하루 전체 누적" — append하면 중복). 대표가 "그게 최종본"이라 하면 다시 넣을 게 없다 — 값은 15:35가 KRX로 찍었고, 그 뒤에 넣은 날이면 ingest가 KRX로 덮는다(원-2026-10-29-18·20). 대체됨(2026-10-29): "같은 파일로 16:00 뒤 재반영(걸음 7)".
- **지난 날짜**(체크포인트로 굳은 날) → 출력에 `[체크포인트] … 전체 재생` 줄이 나오나 본다.
- **새 종목 섹터** — 새 종목이 기타2로 잡힘 → 기존 섹터로 지정(`python fix_sector.py 종목명 섹터` + Supabase watchlist.sector). 고를 땐 네이버 업종(m.stock.naver.com integration `industryCode`·동종 종목)과 기존 섹터 선례로. **고른 섹터를 근거와 같이 한 줄로 묻고, 답을 받은 뒤 지정한다**(섹터 지정은 매번 묻는 다섯 중 하나, 원-2026-10-23-11). 대체됨(10-23): 갈릴 때만 묻기.

## 자주 틀린 곳 (당시 사건 — 반영·캐시) 〔일과에서 옮김 — 줄째〕
- 2026-10-20 같은 날 두 번째 반영 때 외인 DB 점검(걸음 5)을 건너뜀(테스트 창, 옛 뇌) → 같은 날 재반영 때도 DB 점검.
- 종목코드·섹터를 holdings 생성 때만 채웠더니 재계산마다 리셋(시세 조회 느려짐·섹터 "미분류") → 영구 캐시(`stock_code_cache.csv`·`stock_sector_cache.csv`)에서 먼저 조회(옛 §1-3, 설계는 `../설계도실/코드_구조.md`).
- 대표가 받은 매매일지 CSV가 30종목에서 잘려 일부 거래가 통째로 빠짐(파싱 실패가 아니라 파일이 불완전, 옛 §1-6) → 세션엔 맞댈 원본이 없다. 보유 수가 확 줄었나만 보고, 최종 대조는 대표의 메리츠 화면(절차 3).
- `fix_sector.py`는 종목이 아무 데도 없어도 "찾지 못했습니다"를 안 띄운다 — 캐시엔 무조건 써서(`portfolio_core.fix_holding_sector`) 이름 오타가 캐시에 조용히 들어간다 → 고친 뒤 보유 카드에서 그 종목 섹터를 눈으로 본다.
- 섹터 이름 검사가 없다 — `group_sector`는 매핑 밖 이름을 그대로 돌려줘서(`portfolio_core.SECTOR_GROUP_MAP`) 오타가 새 섹터로 잡힌다 → 기존 섹터 목록(`stock_sector_cache.csv`에 이미 있는 이름)과 맞춰 쓴다. 기타·기타2는 2026-10-21부터 비어 있다.
- 짧은 종목코드(< 6자리)는 ingest가 다시 찾는다(`@뇌 신규종목_코드보충`) — 0 날아간 코드도 우연히 걸리지만 dtype 규칙을 대신하지 않는다.
- 2026-08-28 종목코드를 dtype 없이 읽어 앞자리 0이 날아감 → 시세 조회가 조용히 실패(옛 §1-6, 지침서 8절).
