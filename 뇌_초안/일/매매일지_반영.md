# 매매일지 반영

## 설명
- **무엇을 내놓나(끝까지)**: 매매일지를 받으면 숫자를 **만드는** 일이다 — 일하는 사무실은 일과/매매일지_반영 한 장이고, 반영 → 출력 확인 → DB 점검 → 데이터 파일만 커밋까지 묻지 않고 간다. 끝에 대표에게 날짜별 매수·매도 건수, 보유 수, 예수금, 커밋 id와 "메리츠 화면이랑 맞는지 봐 줘" 한 줄. **섹터 지정은 매번 대표에게 한 줄로 묻는다**(원-2026-10-23-11). **두 계좌 맞추기(sync)는 반영한 날마다 묻지 않고 장 마감 뒤**(원-2026-10-26-03 — 대체됨: 매번 묻기 원-2026-10-23-11). 설계도실은 출력이 이상할 때만 내려간다.
- **언제 시키나**: 대표 "넣었어"·"반영해"·"올렸어"(todaytrans/에 메리츠 매매일지 CSV) · 마감본이 와서 같은 날짜를 다시 넣을 때 · 지난 날짜를 다시 넣을 때. 부르는 말: 넣었어, 반영해, 올렸어, 매매일지, 마감본.
  - 파일은 `todaytrans/`에 대표가 넣는다 — 나는 폴더를 감시하지 않으니 말이 있어야 시작한다.
  - 가르는 법:
    - 숫자를 **만드는** 일이면 이 일, **말하는** 일("지금 어때?")이면 `지금_숫자.md`.
    - "이자 들어왔어"·배당 입금이면 CSV가 아니라 입금 행 한 줄 — 세션 장부 C5(데이터센터 게시판).
    - 오늘 첫 대화면 우편함 → 출근 점검이 먼저(지침서 2절).
- **얻을 것과 찾을 곳**(순서 아님 — 어디부터 볼지, 그 게시판에서 어느 사무실을 고를지는 그때 판단, 원-2026-10-27-12 · 위크 1027 「길에서 직접 정보를 빼고 게시판을 보고 판단」)
  - **이 일이 뭔지, 무엇을 하면 안 되나**(저장고·금지·자주 틀린 곳) → `../일과/매매일지_반영.md`(이 일의 무엇) · 입구 `python ingest_daily.py todaytrans/파일 YYYY-MM-DD`. ⚠시점 ⚠dtype — 숫자가 이상하면 holdings를 고치지 말고 transactions를 본다.
  - **외인 DB가 빠짐없이 쌓였나**(하루만 비어도 외인 기간 계산이 틀어진다) — `출근_점검.md`(점검 층만 빌림) · 입구 `python check_daily_db.py`.
  - **무엇을 어떻게 남기나**(데이터 파일만 이름으로 add · 반영한 날마다 장 마감 뒤 sync — 원-2026-10-26-03) → `../일과/기록_올리기.md`(이 일의 무엇)
  - 그 종목이 **사건**인가 — 보유 종목이 무상증자·분할을 했으면 아래 걸음 3b(수량 대조) → 관측소 게시판
  - 지금이 장중인가(`date +%H%M`) — 장중 파일인지가 보고 문장과 다시 넣을지를 가른다.
  - 코드 쪽(설계도실)은 아래 멈춤 "설계도실로 내려갈 때"만 — 평소엔 코드가 한다.
- **걸음** (2026-10-22 일과/매매일지_반영 절차·멈출 때에서 옮김 — 걸음 번호는 다른 장이 부르는 이름이라 그대로)
  1. 파일 이름(예: `todaytrans/1020.csv`)에서 날짜를 읽는다. 날짜는 ingest의 두 번째 인자다 — 스크립트는 파일 이름을 안 보니 세션이 읽어 넣는다(`ingest_daily.main`). 여러 날·같은 날 다시 옴은 아래 멈춤.
  2. `python ingest_daily.py todaytrans/파일 YYYY-MM-DD` — 그 날짜의 기존 반영분을 지우고 이 파일로 바꾼 뒤 재계산(체크포인트 경로). "최근 3일"은 **실행한 날부터 달력 3일**이다(`today − timedelta(days=3)`, `@뇌 safety_days_컷오프`) — 그보다 앞 날은 체크포인트로 굳는다(월요일에 돌리면 금요일이 이미 굳을 수 있다). 굳은 날을 다시 넣어도 ingest가 체크포인트를 버리고 전체 재생한다(`@뇌 체크포인트_막이`, 대표 결정 1 2026-10-21).
  3. 확인 칸대로 출력을 읽는다. 출력이 깨져 보이면 `check_history_alignment(날짜)`를 따로 부른다. ingest 끝 "실제 메리츠 앱 화면과 대조하세요"(`@뇌 메리츠_화면대조`)가 행 잘림을 잡는 유일한 그물이다 — 파서는 열 < 13·행 < 2만 막는다. 세션은 보유 수 급감만 보고, 최종 대조는 대표가 메리츠 앱 화면으로 한다.
  3b. **보유 종목에 무상증자·분할이 있었으면**(그날 공시 · 하루 등락이 가격제한폭 밖) 증권사 CSV 수량과 앱 보유 수량을 대조한다. 거래 반영 코드엔 분할·무상 거래 유형이 없고 매도 분기는 수량 부족을 확인하지 않는다 — 수량이 안 맞은 채 두면 나중에 늘어난 주식을 팔 때 옛 줄을 지우고 (매도가 − 옛 평단) × 판 수량으로 **가짜 큰 실현손실**이 잡힌다(새 뇌 코드 확인 10-26 밤 · 위크 2차 채점 T2, 옛 뇌가 짚음). 안 맞으면 고치지 말고 대표에게(입력은 대표 몫 — 코드 고치기는 이관 뒤, `../대기.md`). [새]
  4. 시세·코드 보충은 ingest가 매번 무조건 한다(`refresh_all_prices`, `@뇌 시세_무조건_갱신`) — 세션은 `[경고]` 줄만 읽는다. 새 종목은 **반영 날 바로** watchlist(csv + Supabase)에 들어가고(ingest 끝 백필), 시세·외인은 **그 종목 시작일부터** 채운다 — 섹터는 비슷한 기존 섹터(기타2 금지)(대표 10-22 17:4x 새 종목 등재 원칙, 「이건 튜즈데이도 마찬가지야」). 섹터가 기타2로 잡히면 아래 멈춤 "새 종목 섹터".
  5. 외인 DB 점검 → `출근_점검.md`(점검 층).
  6. 데이터 파일만 이름으로 묶어 commit·push → `../일과/기록_올리기.md`. **반영한 날마다 묻지 않고 sync** — 장 마감(15:30) 뒤, 장중본이면 16:00 뒤 같은 날짜 재반영 **다음에** `python sync_both_accounts.py` → new1·meritz 두 레포 `both_accounts.csv` 각각 commit·push(대표 「그렇다면 매일해」 원-2026-10-26-03). sync는 VIP 패널 상대 계좌 선용 파일 하나만 다시 쓴다 — Analysis·혼합지수·내 지수는 ingest가 이미 갱신. meritz 칸은 meritz 매매일지가 멈춘 날 뒤로 빈칸 그대로(지어낸 값 없음 — 대표 「매리츠 매매일지는 나중에 빠진거 한번에 다 넣을 게. 그 때 수정하자」). 대체됨(10-26 15:1x): meritz 몰아 넣는 날에만(원-2026-10-26-02) · 대체됨(10-26 아침): 묻고 응이면(원-2026-10-23-11) · 대체됨(10-23): 묻지 않고 sync.
  7c. **케이스북**: 그날 **전량매도로 끝난 사이클**이 있으면 `python casebook.py` → `casebook/` 커밋(수급 게시판 절차 3 "케이스북 갱신" — 사무실은 "주간 리포트 때"라 늦어도 그 주 금요일엔). 사이클 종료 = 그날 판 종목 중 지금 보유 0. 자동으로 부르는 곳이 없다(마지막 커밋 10-20). 〔"옛 뇌가 손으로 하던 정기 일" 쓸기(87 → 새 뇌, 위크 지시 origin 대표 · Week 주민센터 손으로_하던_일_1026)〕 [새]
  7. 대표에게: 날짜별 매수·매도 건수, 보유 수, 예수금, 커밋 id. 장중 파일이면 "장중까지". 끝에 "메리츠 화면 보유 종목 수·예수금이랑 맞는지 한 번 봐 줘" 한 줄 — 맞춰 볼 수 있는 건 대표 화면뿐이라서.
     - **장중에 넣은 날은 16:00 뒤 같은 날짜로 한 번 더 — 마감본이 안 와도 같은 파일로**(위크 결정 2026-10-20). 그래야 asset·sector·index·bigcap 그날 행이 확정 종가로 바뀐다. ingest는 그날 한 행만 쓰므로 다음 날 ingest가 대신 고쳐 주지 않는다. 돌리기 전에 `date +%H%M`이 1600 이상인지 본다(10-22 시연: 15:59에 한 번 먼저 돌아 16:00에 다시 덮음).
  7b. **픽 추적 카드 갱신**: 09:30 아침 리포트가 맨 앞에서 자동으로 갱신한다(`morning_report.main` → `tracking.update`, fff0e63 · 원-2026-10-29-09 — U-024 됨). 반영한 날 장 마감 뒤 숫자로 다시 보고 싶을 때만 손으로 `python tracking.py` → `tracking/`(카드별 CSV + `summary.csv`)를 데이터 파일로 커밋. 그 전엔 자동으로 도는 곳이 없어 10-19 뒤 카드가 멈췄고 ② "트래킹 중" · "근거 사라짐"이 낡은 카드로 나갔다. 〔구멍 실험 5차 F3 — 이관 구멍(위크 확인 10-26 밤)〕
  8. 반영한 날 CFG 태그 종목(`cfg_tagged.csv`)에 매도가 있으면 아래 멈춤 "CFG 매도".
  - 예탁금 이용료·배당금: `transactions.csv`에 `구분=입금`, `수량=1`, `단가=금액`, `메모=예탁금이용료`(배당금은 `종목명=종목`, `메모=배당금`) 한 줄 → 재계산(이 행은 매매일지 재반영으로 안 지워진다). 입금 분기는 종목명을 안 본다 — 예수금만 바뀐다. 장부 칸은 데이터센터 게시판.

## 멈춤
- **멈추고 묻는다**: 파싱 실패 · 보유 수가 크게 이상 · 종목코드가 끝내 안 풀림 · git 충돌이나 내가 안 바꾼 파일. 그 밖엔 묻지 않고 끝까지 — 단 새 종목 섹터 지정은 매번 한 줄로 묻는다(원-2026-10-23-11).
- **파일이 `todaytrans/`에 없다**(대표가 "넣었어"라는데 그 날짜 파일이 없음) → 반영하지 않고 파일 이름·날짜를 묻는다. 옛 파일로 반영하지 않는다. 〔빈 세션 시험 13〕
- **장중 파일** → 보고에 "장중까지", 16:00 뒤 같은 날짜로 한 번 더(마감본이 안 와도 같은 파일로).
- **여러 날** → 오래된 날부터. 같은 날 여러 장이면 가장 늦은 것만.
- **이미 반영한 날이 다시 오면**(장중본 뒤 갱신본 · 여러 날 묶음에 지난 날이 섞임) → **새 것으로 통째로 교체**한다. 대표가 그날 일지를 준 뒤에도 매매해서 갱신본이 새로 온 것이다(대표 10-22 가-3, 원-2026-10-22-07). ingest가 그 날짜 반영분을 지우고 바꾼다(§1-2 "그날 하루 전체 누적" — append하면 중복). 대표가 "그게 최종본"이라 하면 같은 파일로 16:00 뒤 재반영(걸음 7).
- **지난 날짜**(체크포인트로 굳은 날) → 출력에 `[체크포인트] … 전체 재생` 줄이 나오나 본다.
- **새 종목 섹터** — 새 종목이 기타2로 잡힘 → 기존 섹터로 지정(`python fix_sector.py 종목명 섹터` + Supabase watchlist.sector). 고를 땐 네이버 업종(m.stock.naver.com integration `industryCode`·동종 종목)과 기존 섹터 선례로. **고른 섹터를 근거와 같이 한 줄로 묻고, 답을 받은 뒤 지정한다**(섹터 지정은 매번 묻는 다섯 중 하나, 원-2026-10-23-11). 대체됨(10-23): 갈릴 때만 묻기.
- **CFG 매도** — CFG 태그 종목을 **사거나 팔았으면** → `python cfg_track.py`(사이클 카드 다시 만듦 — 매수 날에도, 안 돌리면 `cfg_track/summary.csv`가 낡는다). 매도면 `--sells 날짜`로 그날 줄을 보고 끝에 한 줄(수급 게시판). 〔실전 시험 2b 인바디 · new1-35 검산 10-22 밤〕
- **DB 점검에서 빈 날** → 휴장인지 cron 누락인지 먼저 가른다. `krx_holidays.csv`(휴장일 달력, 2026-10-21 대표 결정 6)에 있으면 휴장이다(정비실 게시판). 없으면 누락이다 — 빈 날 자동 메우기는 다음 cron이 하고, 외인은 5영업일까지만 메워진다(`../일과/출근_점검.md`). 바로 메운다(대표 가-1 ⓐ — `출근_점검.md` 권한, 장중엔 `fill_recent_gaps`만).
- **예수금이 메리츠 앱과 다름**(총매입·총평가는 맞음) → 검산식 **초기자본 − Σ매수 + Σ매도 − Σ매도세 = 예수금**부터 본다. 대개 예탁금 이용료 입금 행이 빠진 것이다 → 대표에게 금액·날짜를 묻고 입금 행 한 줄(C5). 세금(매도세)이 실현손익에 이미 빠져 있다는 건 가치척도 게시판 "매도 수익률 재는 법".
- **VIP 기준가** — 대표가 VIP 기준가도 같이 불러 줌 → **대표가 숫자를 불러 주면 그대로 넣는다 — 대략값(「1715여」)이면 한 줄 확인, 숫자 없이 "넣어"면 값을 묻는다**(원-2026-10-27-11 — 원-2026-10-23-11 「매번 물어야함」을 좁힘) → 세션 장부 C4(new1·meritz **두 레포**에 같이).
- **같은 날짜를 다시 넣었는데 신규 0건** → ingest가 거래 저장 전에 끝난다(`@뇌 매매0건_종료`) — 그날 옛 반영분이 그대로다. 멈추고 "신규 0건, 옛 반영분 유지"로 보고한다. 단 끝나기 전에 **지수 · 대형주 · 벤치는 그날 확정 종가로 찍는다**(77adf6e · 원-2026-10-29-05 — 거래 없는 날도 index·bigcap·bench가 안 멈추게, 보유 · 예수금 · asset은 안 건드림). 벤치는 더 늦은 날이 이미 있으면 locked.
- **`[⚠️ 정합성] … 뒤처짐`** → **멈추지 않는다**. 어느 파일이 어느 날짜에서 멈췄나 보고 파일별로 고친다(`../일과/매매일지_반영.md` "멈출 때" — 검사는 경고만, 고치는 건 세션). 왜 생기나는 관측소 게시판(lock-step 재발), 백필은 설계도실 게시판(backfill_bigcap_history · 일별시세). 고치는 길: 그날 매매일지 재반영(asset·sector·index·bigcap 한꺼번에), `backfill_bigcap_history.py`(빠진 날만, 있는 행은 안 고침), 있는 행은 `fetch_daily_price_history` 확정 종가 → `snapshot_*(on_date=날짜)`로 손으로 — 보정 도구는 따로 없다. `compute_metrics_at_close`는 **지금 보유**로 계산하니 지난 날짜 asset엔 쓰지 않는다. 고치는 법을 모르는 파일일 때만 묻는다. ⚠시점
- **설계도실로 내려갈 때**(출력이 이상할 때만):
  - `[체크포인트]` 줄이 나왔거나 보유 수·평단이 장중본과 이상하게 다름 → 설계도실 게시판 §6-14(재생 체크포인트: 최근 3일은 늘 재생, 체크포인트 날짜 이하 재반영이면 전체 재생). holdings를 손대지 않는다.
  - 파싱 실패·종목 수가 크게 모자람 → 설계도실 게시판 §1-6(cp949 순서·열 위치·서브헤더·30개 잘림 전례).
  - 고친 섹터가 다음 반영에 옛 값으로 돌아감 → 설계도실 게시판 §6-24 + 설계도실 게시판 §1-3(캐시 분리) — checkpoint_holdings까지 같이 고쳤나(`fix_sector.py`가 세 파일 동시).
  - 종목코드가 끝내 안 풀림·앞자리 0 유실 → 설계도실 게시판 §1-3 · 인라인 스크립트면 `dtype={"종목코드": str}`. ⚠dtype

## 권한
- **바로 해도 됨**
  - 반영 → 출력 확인 → DB 점검 → 데이터 파일만 커밋·push(걸음 1~8).
  - sync — 묻지 않는다(걸음 6, 원-2026-10-26-03 — 대체됨: 매번 묻기).
  - 새 보유 종목을 watchlist(Supabase)에 넣는 ingest 끝 백필 — 대표가 정한 자동 등재(10-22 「반영 날 바로」)라 따로 묻지 않는다 — 빈 날 메우기(원-16)와 같은 자리.
  - 정합성 뒤처짐 파일별로 고치기(고치는 법을 아는 파일).
- **안 함**
  - holdings 손대기 — 숫자가 이상하면 transactions를 본다.
  - 새 섹터 만들기(대표 2026-10-21).
  - 무상증자·분할 수량이 안 맞을 때 고치기(걸음 3b — 대표에게).
  - 옛 파일로 반영하기.
  - `compute_metrics_at_close`를 지난 날짜 asset에 쓰기.
- **대표 몫**: 새 종목 섹터(한 줄로 묻고 답 뒤 지정) · 메리츠 화면 최종 대조 · 분할·무상 수량 입력 · 예탁금 이용료 금액·날짜 · VIP 기준가 값.
