## 절차
0. 전날 HISTORY 파일이 없으면(대표가 퇴근 말 없이 끝난 날) 전날 치부터 쓴다 → `기록_올리기.md` 걸음 5.
1. `python check_daily_db.py [일수]` — 테이블 셋의 날짜별 적재 수와 빠진 종목. 날짜 목록은 price_history에 **들어 있는** 날짜 상위 N개다(`check_daily_db.py:38-43`) — 맨 위 날짜 = "DB에 들어온 마지막 날"이지 오늘이 아니다. 크론이 늦었는지는 그 날짜와 지금 시각을 보고 사람이 판단한다.
2. 읽는다: price_history·investor_flow는 날짜마다 watchlist 수 — 기준 숫자는 셀에 박지 않고 출력 **첫 줄 값**(Supabase `watchlist`, `check_daily_db.py:34-35`; 10-20엔 181)과 맞댄다. market_flow는 KOSPI·KOSDAQ 행이 **있는지만** 본다(값이 0인지는 안 본다, `check_daily_db.py:51-62`). 빠진 종목 이름은 최근 날짜만 찍힌다.
   - 크론의 90%(`GAP_MIN_RATIO = 0.9`, 181이면 162)는 "빠진 날" **자동 메우기 문턱**이다(`db_fetch_daily_prices.py:179·204`) — 보고 기준이 아니다. 보고는 숫자가 아니라 종목명으로: 한두 개면 거래정지인지 짚고, 여럿이면 원인부터(세션 값·출처 없음).
   - 휴장일에 생긴 가짜 행은 181/181로 정상처럼 보인다 — 날짜가 휴장일인지 달력과 맞대야 보인다.
3. 모자라면 원인을 짚는다: 거래정지(정상), 휴장(정상), 크론이 안 돎, 네이버 응답 형식 변경.
4. 대표에게 한두 줄로 보고(세션 첫 대화, 대표 2026-10-01 지시).

## 멈출 때
- 거래일 하나가 통째로 비었다 → **check_daily_db로는 이게 안 보인다**(자기 날짜 목록이라 빈 날은 줄 자체가 없다). GitHub Actions 로그의 "8) 최근 5거래일 빈 날 점검" 줄(`db_fetch_daily_prices.py:195`)이나 index_history 날짜·달력과 맞대야 보인다. 보이면 `python db_fetch_daily_prices.py`로 메울지 대표에게. Actions 이력은 `git credential fill`로 얻은 토큰 + curl로 API를 부른다(마지막으로 쓴 게 2026-08-25, 지금 되는지 미확인 — 세션 값·출처 없음).
- investor_flow가 5영업일 넘게 비었다 → 그 사이는 못 메운다는 걸 대표에게. 출처 API가 최근 5영업일치만 준다(`db_fetch_daily_prices.py:192-193` docstring, `../설계도실/인프라_크론.md`).
- 한 테이블만 며칠째 안 쌓인다 → 출처 페이지가 바뀐 것. 코드 수정은 제안부터.
- 휴장일 가짜 행을 찾았다 → DB 행 삭제는 대표 승인 뒤(2026-10-06 전례: 10/5 price_history 180행·market_flow 0행 2개 삭제). 휴장 판정이 실패(None)하면 크론은 거래일로 보고 적재를 막지 않는다(`portfolio_core.py:107-127`).

## 끝났다는 확인 / 산출물
- 대표에게: 세 테이블의 직전 거래일 적재 수 + 빠진 종목과 그 이유. 파일은 안 남긴다.

## 금지
- GitHub Actions "success"만 보고 정상이라 하지 않는다 — 방어 구조라 일부 단계가 실패해도 성공으로 찍힌다.
- 거래정지 한 종목(예: 해태제과식품)이나 휴장일을 오류로 보고하지 않는다.
