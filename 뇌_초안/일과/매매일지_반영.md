# 매매일지 반영

트리거: 대표가 "넣었어"·"올렸어"(todaytrans/에 매매일지 CSV). 지난 날짜 매매일지를 다시 넣을 때(체크포인트 날짜 이하면 ingest가 알아서 전체 재생 — 출력의 `[체크포인트]` 줄 확인). 예탁금 이용료(입금)가 들어왔을 때
한 문장: 매매일지는 그날 하루 전체의 누적이라 같은 날짜를 통째로 바꿔 넣고, 반영 → 확인 → 외인 DB 점검 → push를 묻지 않고 끝까지 한다.
상태: 시험판(형식 B) · 마지막 확인 2026-10-21
이 셀 안 (게시판 → 이 머리 → 필요한 칸만 펼친다):
- 절차 — 날짜순으로 ingest → 결과 확인(보유 수·예수금·정합성) → 코드 없는 종목 → DB 점검 → commit·push
- 멈출 때 — 파싱 실패, 보유 수가 크게 이상, 코드가 끝내 안 풀림, git 충돌
- 끝났다는 확인 / 산출물 — 정합성 OK, 커밋 하나, 대표에게 날짜별 매수·매도 건수
- 금지 — holdings 손으로 고치기, append, dtype 없이 종목코드 읽기, 섹터를 인라인으로 고치기
- 자주 틀린 곳 — lock-step 재발 1~7(당시 사건)
- 무엇으로 재나 — `ingest_daily.py`, `check_history_alignment`, `fix_sector.py`

## 절차
이 일의 길 = `../길/매매일지_반영.md`
1. 파일 이름(예: `todaytrans/1020.csv`)에서 날짜를 읽는다. 여러 날이면 **오래된 날부터** 차례로. 날짜는 ingest의 두 번째 인자다 — 스크립트는 파일 이름을 안 보니 세션이 읽어 넣는다(`ingest_daily.main`). 같은 날 여러 장이면 가장 늦은 것(세션 값·출처 없음).
   - **마감본 교체는 그날 첫 ingest로 하는 게 기본** — 2026-10-21부터는 3일이 지나 체크포인트로 굳은 날을 다시 넣어도 ingest가 체크포인트를 버리고 전체 재생한다(`@뇌 체크포인트_막이`, 대표 결정 1). 대체됨(2026-10-21): "3일 안 첫 ingest가 유일한 막이"(위크 판정 07·09·10).
2. `python ingest_daily.py todaytrans/파일 YYYY-MM-DD` — 그 날짜의 기존 반영분을 지우고 이 파일로 바꾼 뒤 재계산(체크포인트 경로). "최근 3일"은 **실행한 날부터 달력 3일**이다(`today − timedelta(days=3)`, `@뇌 safety_days_컷오프`) — 그보다 앞 날은 체크포인트로 굳는다. 월요일에 돌리면 금요일이 이미 굳을 수 있다는 뜻이다. 3이라는 숫자의 근거는 docstring에 없다(세션 값·출처 없음).
3. 확인: 보유 종목 수(급감했나)·예수금·`[정합성 OK]`(asset·sector·index·bigcap 마지막 날짜가 같은가). 출력이 깨져 보이면 `check_history_alignment(날짜)`를 따로 부른다. ingest 끝 "실제 메리츠 앱 화면과 대조하세요"(`@뇌 메리츠_화면대조`)가 행 잘림을 잡는 유일한 그물이다 — 파서는 열 < 13·행 < 2만 막는다(`portfolio_core.parse_daily_trade_csv`). 세션은 보유 수 급감만 보고, 최종 대조는 대표가 메리츠 앱 화면으로 한다(세션 값·출처 없음).
4. 시세·코드 보충은 ingest가 매번 무조건 한다(`refresh_all_prices`, 2026-09-17, `@뇌 시세_무조건_갱신`) — 세션은 출력의 `[경고]` 줄만 읽는다. 새 종목은 ingest 끝에서 watchlist에 자동 편입. **새 종목이 섹터 캐시에 없으면 기타2로 잡힌다** — 2026-10-21부터 기타·기타2는 비워 두므로, 네이버 업종(m.stock.naver.com integration `industryCode`·동종 종목)과 기존 섹터 선례로 골라 `python fix_sector.py 종목명 섹터` + Supabase `watchlist.sector`도 맞춘다. 새 섹터는 만들지 않는다(대표 2026-10-21). 판단이 갈리면 대표에게 한 줄로 묻는다.
5. 외인 DB 점검 → `출근_점검.md` 절차 1~3.
6. 데이터 파일만 묶어 commit·push → `기록_올리기.md`. 장 마감(15:30) 뒤 반영이면 `python sync_both_accounts.py` → 두 레포 `both_accounts.csv` 각각 commit·push(같은 곳 절차 4).
7. 대표에게: 날짜별 매수·매도 건수, 보유 수, 예수금. 장중 파일이면 "장중까지"라고 밝힌다(마감본이 오면 같은 날짜로 다시 넣는다).
   - **장중에 넣은 날은 16:00 뒤 같은 날짜로 한 번 더 넣는다 — 마감본이 안 와도 같은 파일로**(위크 결정 2026-10-20). 그래야 asset·sector·index·bigcap 그날 행이 확정 종가로 바뀐다. ingest는 그날 한 행만 쓰므로 다음 날 ingest가 대신 고쳐 주지 않는다. 관행(커밋 406143d·e6e6170)으로만 하던 일이고, 16:00 문턱은 2026-09-14 하루 관측이 근거다(세션 값·출처 없음).
(대체됨 2026-10-20 위크 결정: 반영마다 cfg_ask로 CFG 태그 묻기 — 대표가 말해 주는 게 원칙이라 잔소리가 됨 → 주간 리포트 3-2로 옮김)
8. 반영한 날 CFG 태그 종목(`cfg_tagged.csv`)에 매도가 있으면 `python cfg_track.py --sells 날짜` → 보고 끝에 그대로 한 줄("외인 보고 산 X — 사이클 끝(전량)/일부 매도, 결과 %·태그가 대비 %"). 전량이면 `../수급/외인_매수_복기.md`의 끝난 사이클(CFG vs Others·casebook에 자동). (10-20 섀도: 인투셀 전량 매도가 "매도 1건"으로만 보고됨)
- 예탁금 이용료·배당금: `transactions.csv`에 `구분=입금`, `수량=1`, `단가=금액`, `메모=예탁금이용료`(배당금은 `종목명=종목`, `메모=배당금`) 한 줄 → 재계산(이 행은 매매일지 재반영으로 안 지워진다). 입금 분기는 종목명을 안 본다 — 예수금만 바뀐다(`portfolio_core.apply_transaction`). 지금 입금 5행 = 예탁금이용료 1 + 배당금 4(한국단자·영원무역·동서·CJ제일제당).

## 멈출 때
- 파싱 실패, 보유 수가 크게 이상, 코드가 끝내 안 풀림, git 충돌 — 이때만 대표에게 묻는다. 그 밖엔 묻지 않고 끝까지(대표 지시).
- `[정합성]`에 뒤처진 파일이 있으면 어느 날짜가 비었는지 보고 파일별로 고친다. 검사는 경고만 하고 고치지 않는다(`check_history_alignment`). 고치는 길: 그날 매매일지 재반영(asset·sector·index·bigcap 한꺼번에), `backfill_bigcap_history.py`(빠진 날만 채우고 있는 행은 안 고침), 있는 행을 바로잡을 땐 `fetch_daily_price_history`로 확정 종가를 받아 `snapshot_*(on_date=날짜)`로 손으로 — 따로 보정 도구는 없다. `compute_metrics_at_close`는 **지금 보유**로 계산하니 지난 날짜 asset엔 쓰지 않는다.
- **같은 날을 다시 넣었는데 신규 거래 0건**이면 ingest가 저장 전에 끝난다(`n_new == 0` → `sys.exit(0)`, `@뇌 매매0건_종료`) — 그날 옛 반영분이 그대로 남는다. 멈추고 대표에게 묻는다(어떻게 처리할지는 대표 답 대기).

## 끝났다는 확인 / 산출물
- 정합성 OK + 데이터 커밋 하나(메시지에 날짜들) + 대표 보고 한 덩어리.
- 보유 수·예수금이 메리츠 앱과 같은지는 대표가 맞댄다 — 세션이 맞댈 원본이 없다(세션 값·출처 없음). 진실은 재생 실현손익이다(§1-1); 매매일지의 `실현손익_증권사` 칸은 파싱만 하고 2026-09-08 이후 맞대 본 적 없다.

## 금지
- todaytrans 스테이징·세션이 push·backup 폴더 안전망 흐름은 메모리 `project_workflow` 그대로.
- holdings(보유)를 손으로 고치지 않는다 — transactions 재생이 유일한 진실(줄기 §2-5).
- 같은 날짜를 append하지 않는다 — 누적이라 중복된다(§1-2, 네이버 1주 → 3주).
- 임시 스크립트로 종목코드를 읽을 때 `dtype={"종목코드": str}` 없이 읽지 않는다(줄기 §2-6).
- 섹터를 인라인 스크립트로 고치지 않는다 → `python fix_sector.py 종목명 섹터`(세 파일 + 체크포인트 동시).
- **체크포인트 날짜 이하를 다시 넣으면 출력의 `[체크포인트] … 전체 재생` 줄을 확인한다.** ingest가 넘긴 날짜(`replaced_date`)가 `checkpoint_state.csv`의 체크포인트날짜 이하면 체크포인트를 버리고 처음부터 재생한 뒤 새 체크포인트를 저장한다(`@뇌 체크포인트_막이`, 테스트 `test_incremental_replaced_date_at_or_before_checkpoint_replays_from_scratch`, 대표 2026-10-21 "오케이"). 그 줄이 없는데 옛 값이 남으면 막이를 안 탄 것 — ingest를 거치지 않고 transactions.csv를 손댄 경우다. 대체됨(2026-10-21): "그냥 다시 넣지 않는다 — 넣어도 옛 값이 남고 경고도 없다, 체크포인트 두 파일을 지우고 재생"(재생 범위 `> ckpt`는 `@뇌 체크포인트_없을때`).
- **2026-08-03~08-13 매매일지는 넣지 않는다.** 그 기간 229행은 `메모=초기 히스토리`라, 교체 대상(`메모==일일매매일지`)이 아니어서 교체가 아니라 쌓인다(1주 → 3주와 같은 모양, `portfolio_core.DAILY_IMPORT_TAG`·`portfolio_core.import_daily_trades`).
- **fee_rate·초기자본을 바꾸면 체크포인트 두 파일을 지우고 재생한다** — 체크포인트 예수금엔 옛 비율로 계산된 값이 박혀 있다(`@뇌 체크포인트_자본덮어씀`, 선례 2026-09-08: 누적 410,291 → 405,218). fee는 매도금액에만 0.002(2026-09-08부터).

## 자주 틀린 곳 (당시 사건 — 반영·캐시)
- 2026-10-20 같은 날 두 번째 반영 때 외인 DB 점검(걸음 5)을 건너뜀(테스트 창, 옛 뇌) → 같은 날 재반영 때도 DB 점검.
- 종목코드·섹터를 holdings 생성 때만 채웠더니 재계산마다 리셋(시세 조회 느려짐·섹터 "미분류") → 영구 캐시(`stock_code_cache.csv`·`stock_sector_cache.csv`)에서 먼저 조회(옛 §1-3, 설계는 `../설계도실/코드_구조.md`).
- 대표가 받은 매매일지 CSV가 30종목에서 잘려 일부 거래가 통째로 빠짐(파싱 실패가 아니라 파일이 불완전, 옛 §1-6) → 세션엔 맞댈 원본이 없다. 보유 수가 확 줄었나만 보고, 최종 대조는 대표의 메리츠 화면(절차 3).
- `fix_sector.py`는 종목이 아무 데도 없어도 "찾지 못했습니다"를 안 띄운다 — 캐시엔 무조건 써서(`portfolio_core.fix_holding_sector`) 이름 오타가 캐시에 조용히 들어간다 → 고친 뒤 보유 카드에서 그 종목 섹터를 눈으로 본다.
- 섹터 이름 검사가 없다 — `group_sector`는 매핑 밖 이름을 그대로 돌려줘서(`portfolio_core.SECTOR_GROUP_MAP`) 오타가 새 섹터로 잡힌다 → 기존 섹터 목록(`stock_sector_cache.csv`에 이미 있는 이름)과 맞춰 쓴다. 기타·기타2는 2026-10-21부터 비어 있다.
- 짧은 종목코드(< 6자리)는 ingest가 다시 찾는다(`@뇌 신규종목_코드보충`) — 0 날아간 코드도 우연히 걸리지만 dtype 규칙을 대신하지 않는다.
- 2026-08-28 종목코드를 dtype 없이 읽어 앞자리 0이 날아감 → 시세 조회가 조용히 실패(옛 §1-6, 줄기 §2-6).
