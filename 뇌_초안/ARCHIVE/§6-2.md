## 6-2. 일일 매매일지 반영 흐름 (todaytrans/)
- `todaytrans/` 폴더는 로컬 전용 스테이징 폴더 (`.gitignore`에 등록, git에는 안 올라감).
- 사용자가 증권사(메리츠) 매매일지 CSV를 `todaytrans/transactions.csv`에 덮어써서 넣어둔다.
  **세션은 이걸 실시간으로 감지하지 못하므로, 사용자가 "넣었어" 같은 짧은 메시지로 알려줘야 한다.**
- 반영 절차: `python ingest_daily.py todaytrans/transactions.csv <YYYY-MM-DD>` 실행
  (날짜는 보통 그날 당일) → 스크립트가 해당 날짜의 기존 반영분을 지우고 이번 파일로 교체 후
  전체 재계산 → 결과(보유종목 수/현금/평가금액/총자산) 확인 → 코드 미확인 종목 있으면
  `core.refresh_all_prices()`로 보충 → git commit/push.
- **이 4단계(반영→확인→코드보충→push)는 검증된 흐름이므로 매번 물어보지 말고 바로 진행할 것.**
  파싱 실패, 보유종목 수가 크게 이상함, 코드가 끝내 안 풀림, git 충돌처럼 실제 문제가 있을
  때만 멈추고 사용자에게 확인받는다.
- **매매일지 반영할 때마다 외인 DB(Supabase `investor_flow`)도 같이 확인할 것** (2026-10-01 사용자 지시).
  직전 거래일까지 날짜가 빠짐없이 있는지, 날짜별 종목 수가 watchlist(약 180)와 맞는지 본다.
  이 데이터는 Foreigner 응용("비기", §6-28 Link 확장 예정)이 "일정 기간 외인 비중 변화"를 계산하는
  근거라 하루만 비어도 기간 계산이 틀어진다(9/10~11 네이버 개편으로 이틀치 통째 누락 전례, §6-9).
  거래정지 종목은 네이버가 거래량을 "-"로 줘서 그날 행이 정상적으로 빠진다 — 해태제과식품이
  2026-09-17부터 거래량 0·종가 고정으로 179/180이 된 사례(오류 아님). 빠진 게 있으면 원인을 짚어 사용자에게 알린다.
  점검 스크립트: `python check_daily_db.py [일수]` (price_history/investor_flow/market_flow 날짜별 적재 수 + 빠진 종목).
  **세션 첫 대화에서 이 점검 결과를 먼저 보고한다**(2026-10-01 사용자 지시, 매일).
- **"히스토리 파일 lock-step" 반복 문제 (지금까지 3번: index_history ×2 §6-17, bigcap_history ×1 §6-19)**: **(낡음 — 2026-10-20 위크 확인: 아래 기록은 7번째 재발까지 있다. "3번"은 이 문단을 처음 쓴 때 숫자)**

  겪음: GS리테일이 9/15 17:20 시점 값(등락률 -5.79%)으로 이틀 넘게 멈춰있었는데, §6-34
  Today's Alarm이 이 stale 등락률을 "오늘 -5.8% 급락"으로 표시함(사용자가 "차트 보면
  그렇게 안 빠졌는데?"라고 지적해서 발견 — 실제로 라이브 재조회하니 -0.21%였음).

  asset_history/sector_history엔 영향 없다.
