# 앱 운용 — 앱 자료가 언제 어떤 순서로 쌓이나

## 설명
- **무엇을 주나**: 앱 자료가 언제 어떤 순서로 갱신되고 쌓이나를 볼 때 어느 장을 열지, 그리고 배포판·로컬이 어긋날 때 진단하는 꼴.
- **도움 될 때**: 새로고침·Setting·캐시·갱신 순서를 고치거나 설명할 때 · 매매일지 반영으로 무엇이 어떤 순서로 쌓이나 볼 때 · 화면 숫자가 언제 본 값인지 따질 때 · 배포판만 에러가 날 때 · "최근 작업이 뭘 깨뜨렸나" 의심될 때.
- **이 사무실에 사는 장**
  | 이런 상황이면 | 이 장이 도움이 될 수 있어 |
  |---|---|
  | Setting · 새로고침 · ui_cache · 휴장일 스냅샷 | `새로고침과_캐시.md` |
  | 화면 숫자가 언제 값인가 | `../인식의_방/앱_숫자는_보는_시점.md` |
- **진단할 때 — 생김새**
  - 배포판만 에러가 나고 로컬·새 가상환경 재현이 다 통과하면 대표에게 **Manage app → Reboot app**을 부탁하고, 에러가 애매하면 그 "Manage app" 로그 화면 캡처부터 요청한다(리댁트 안 된 원문이 거기 있음 — 세션은 Streamlit Cloud 로그인 불가). [옮김] 옛 claude.md 393–397 (§6-1-2)
  - `Desktop/backup` 스냅샷을 Git Bash에서 robocopy로 갱신할 땐 `MSYS_NO_PATHCONV=1`을 앞에 붙인다 — 안 붙이면 `/E`가 `E:/`로 바뀌어 깨진다(`MSYS_NO_PATHCONV=1 robocopy SRC DST /E /XD .git __pycache__ /XF *.pyc`). 갱신 여부는 대표에게 확인. [옮김] 옛 메모리 `project_workflow.md` 66–69행
  - "최근 작업이 뭘 깨뜨렸나" 의심엔 일반론으로 답하지 말고 **`git log -p`로 그 함수의 실제 변경을 감사한 뒤** 답한다 — 무엇이 바뀌었고 안 바뀌었는지 정확히 보이는 게 더 설득력 있고, 진짜 원인(무관한 옛 구멍)이 드러나기도 한다(2026-08-24 `watchlist_prices.csv` — claude.md엔 "커밋되는 영구 데이터"라 적혀 있었는데 한 번도 커밋된 적 없었음). 앱이 직접 쓰는 파일은 `git ls-files`로 실제 커밋 여부부터 본다. [옮김] 옛 메모리 `feedback_check_uncommitted_local_state_files.md` 13–15행

## 이유
- 배포판 캐시는 새 커밋 푸시로는 안 지워지고 "Reboot app"만 지운다 — 2026-09-05 겪음(옛 claude.md §6-1-2).
- 문서에 적힌 것과 실제 커밋이 다를 수 있다 — 2026-08-24 `watchlist_prices.csv`(옛 메모리 `feedback_check_uncommitted_local_state_files`).

## 적용 예
> 예는 규칙이 아니다.
- **배포판만 ImportError (2026-09-05)**: 로컬·새 가상환경 재현이 다 통과했는데 배포판만 `append_capture_anomalies`를 못 찾았다 — 빈 커밋을 더 푸시해도 같았고 대표가 Reboot app을 누르니 풀렸다.
- **커밋 안 된 파일 (2026-08-24)**: "커밋되는 영구 데이터"라 적힌 `watchlist_prices.csv`가 한 번도 커밋된 적 없었다 — `git ls-files`로 먼저 봤으면 바로 보였다.
