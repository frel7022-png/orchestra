# 데이터센터 — 1층 게시판
주민: C-0055 데이터센터_게시판

**데이터센터 = CSV + Supabase + 세션 장부 + 앱 화면. DB만 아님.** (코드에서 "DB"는 Supabase 하나만 뜻한다 — 여기선 자료 전부.)

이 빌딩은 **무엇이 어디에 있고, 언제 어떻게 쌓이고, 어떻게 꺼내나**를 다룬다. 앱은 자료의 집합체라 앱 설명도 여기 산다(대표 원-2026-10-21-18).
층 자리: 판단(바라보는 눈·가치척도·기법·추천·운용·인식의 방) / 읽기(수급) / **데이터센터**(관측소 포함, 2026-10-28) / 바닥(도서관·사례 저장고·병원 기록·정비실 고장 절차·설계도실 코드 구조 — 여기선 가리키기만).
가르는 법: 이 빌딩은 "있다·언제 쌓이나·꺼낸다"와 그 안 관측소의 "어떻게 재나·함정", 수급·바라보는 눈은 "뜻·판단".

MD는 이름이 정체, 사무실은 지금 주소다 — "보유_카드는 지금 앱 기능 사무실에 있다"(대표, 원-2026-10-21-21). 주소가 바뀌면 이 표와 주민센터(`../뇌관리/주민센터.md`)만 고친다.

앱을 고칠 때 걸음은 `../일/앱_고치기.md`(화면 글자 → 패널 사무실 → 설계도실 → 렌더링_함정). 앱을 고칠 때 대표와의 약속 다섯([옮김] 옛 메모리 다섯):
- 스펙은 대표 설명이 끝나고 되읽어 동의받은 뒤 착수 — 2026-09-08 VIP를 메인 패널에 끼웠다가 "전용 섹션을 원했다"(`feedback_confirm_spec_before_implementing`).
- 구조 결정(파일 쪼개기·함수 옮기기)은 코드 전에 `report/`에 리포트 — 왜 필요한지 · 구조도 · 안 셋과 각 장점 · "이 방향이면 이 안" 추천, 대표가 고른 뒤 구현. 대표도 구조를 알아야 지시가 정확해진다(2026-10-01, `feedback_structure_decisions_as_report` 2–4행).
- 고치다 **우연히** 본 하드코딩·중복·비효율은 몇 문장으로 "뭐가 문제고 고치면 뭐가 좋아지나"를 말하고 승인 뒤 고친다 — 대표 학습용: 「이런게 겹쳐있거나 그런건 너가 합리적으로 바꾸기 전에 물어봐서 왜 고쳐도 되는지 그럼 어떤 이득이 생기는지 나에게 설명해주면 나도 점점 컴퓨팅에 이해도가 높아지고 좋아질 거 같은데」(2026-08-25). 일부러 찾아다니라는 뜻은 아니고, 사소한 스타일은 넘긴다(`feedback_explain_before_fixing_code_quality` 11–13·20–34행).
- 이름이 좁게 스코프된 기능은 엣지케이스로 넓히자고 하지 않는다 → `앱_기능.md` "기능을 넓히자고 할 때"(`feedback_scope_features_to_their_name`).
- 자동 테스트는 이미 있다(`tests/`, `../설계도실/코드_구조.md` §6-11) — 계산 로직을 고치면 테스트 케이스를 같이 넣는다(옛 "테스트 필요해지면 먼저 알려라" `feedback_flag_when_tests_needed`는 이걸로 대체됨).

헷갈릴 때 고르는 법:
- 패널이 **무엇을 거르나** → 스크리너 / **무엇을 그리나** → 분석 패널 / **언제 갱신되나** → 새로고침과 캐시
- 패널 숫자를 **어떻게 재나** → 여기 말고 `관측소/_게시판.md`
- **세팅(숫자 집 `세팅.md`) ≠ 앱 Setting 버튼**(새로고침 한 번에, `새로고침과_캐시.md`) — 이름만 같다.
